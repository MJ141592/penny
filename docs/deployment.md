# Deploying Penny

The runbook. Start to finish, from an empty Railway workspace to a working deployment, with no
step that exists only in someone's shell history.

**The contract:** a teammate with this repository can reproduce the whole deployment knowing
exactly two values — an **OpenAI API key** and a **domain**. Everything else is generated by
`infra/provision.py`, derived from the project's own topology, or a default in
`backend/app/config.py` that is deliberately not set on Railway at all.

Related documents, cross-linked rather than repeated:

- [`infra/variables.md`](../infra/variables.md) — the authoritative variable manifest, one class per
  variable, and why each is allowed to exist.
- [`docs/railway-deployment.md`](./railway-deployment.md) — the platform reference: topology
  reasoning, the GOWA webhook contract, the two-databases decision, cost.
- [`docs/gowa-runbook.md`](./gowa-runbook.md) — pairing a WhatsApp account. Needs a physical phone.
- [`docs/security.md`](./security.md) — the settings only a human can change.

## 1. Prerequisites

| | |
|---|---|
| Railway CLI | `brew install railway` — verified against **5.27.0** |
| A Railway login | `railway login` |
| A workspace that can create projects | **not** the personal workspace if its trial has expired; see [Traps](#things-that-will-bite-you) |
| A verified GitHub account on Railway | railway.com/verify, **before** deploying. An unverified account gets a Limited Trial with *"restricted outbound network access and only a limited set of ports"*, which breaks GOWA's WhatsApp websocket. Go straight to Hobby. |
| An OpenAI API key | platform.openai.com/api-keys |
| A domain, and the ability to add a CNAME to it | |
| Python 3.9+ | stdlib only — the macOS system `python3` is enough; the provisioner imports nothing you have to install |

Find your workspace id:

```sh
railway list --json | python3 -c "import json,sys;print({p['workspace']['id']:p['workspace']['name'] for p in json.load(sys.stdin)})"
```

## 2. Provision

```sh
export OPENAI_API_KEY=sk-...
infra/provision.py --workspace <workspace-id> --domain penny.example.com --dry-run   # look first
infra/provision.py --workspace <workspace-id> --domain penny.example.com
```

`OPENAI_API_KEY` is read from the environment **only** — never a flag, because argv is visible to
`ps` and lands in shell history.

That one command creates the project, the Postgres addon, the `gowa` service with its image, its
variables and its volume, the `penny` service, every generated secret, the domain, and the GitHub
source connection. What it prints at the end is the list of things a script cannot do for you.

It is **idempotent**. Run it again after a change, or when you are not sure what state something is
in; it converges rather than duplicating. Specifically:

- Project, services, volume and domain are created only when absent.
- Generated secrets are minted only when the key is missing on the service. A second run does not
  reissue `SESSION_SECRET` — that would log every household out.
- `WHATSAPP_WEBHOOK_SECRET` / `GOWA_BASIC_AUTH` are written to **both** services from one value. If
  the two sides are ever found disagreeing, it says so loudly and converges gowa onto penny's value.
- Literal infra values (`ENV`, `PORT`, `GOWA_URL`, `APP_HOST`, …) are enforced: drift is reset.
- `${{Postgres.…}}` references are written only when absent, because Railway reports them *resolved*
  and a comparison against the literal would rewrite them on every run.

Useful flags:

| | |
|---|---|
| `--dry-run` | Reads Railway for real, prints every mutation it *would* make, changes nothing. |
| `--self-test` | Offline. Proves secret constraints, the `${{…}}` round-trip, the idempotence arithmetic, and that the script writes nothing `config.py` calls a code default. No network. |
| `--prune` | Deletes variables that only restate a `code_default()` — see [the levers](#operational-levers). |
| `--no-deploy` | Provision without triggering a deploy. |
| `--repo ''` | Deploy by upload (`railway up`) instead of connecting GitHub. Only for a throwaway. |

### The secrets it prints

Once, at the end, to stdout, under a banner. They are already stored on Railway and **the script
will never print them again** — it does not write them to a file, in this repo or anywhere else.
Put them in the password manager before you close the terminal.

Losing them is survivable but not free: you can mint new ones
(`railway variable set SESSION_SECRET --stdin --service penny`), at the cost of logging every
household out, and re-pairing the webhook secret across both services.

## 3. The human steps

The script ends by printing these. They are not optional; the deployment is not finished without
them.

1. **DNS.** Add the CNAME the script prints (`railway domain status <domain> --service penny --json`
   reprints it). TLS is issued only after it propagates.
2. **Pair the WhatsApp account** — [`docs/gowa-runbook.md`](./gowa-runbook.md). Needs a physical
   phone and a **secondary** WhatsApp account, never a primary. The procedure attaches a temporary
   public domain to `gowa`; **delete it afterwards**, because `/health` and `/statics` sit outside
   GOWA's basic auth and the login QR PNG is publicly fetchable while it is up.
3. **Set an OpenAI spend cap** at platform.openai.com/settings/organization/limits. This is the one
   guard no bug in this repository can bypass. `IMPORT_MAX_SPEND_USD` and
   `LLM_MONTHLY_BUDGET_USD_PER_HOUSEHOLD` are the in-app guards; they are code, and code has bugs.

## 4. Verify

```sh
DOMAIN=penny.example.com
```

**Health** — liveness only; it never touches the database, so that a Postgres blip cannot become a
restart loop:

```sh
curl -fsS https://$DOMAIN/api/health          # {"status":"ok"}
```

**The SPA** — served same-origin by the same service, from `/app/static` in the image:

```sh
curl -fsS https://$DOMAIN/ | head -5          # <!doctype html> …
```

**An authenticated request.** `/api/me` is the smallest thing that proves the session cookie, its
signing secret and the database are all working together:

```sh
curl -fsS -c /tmp/penny.jar -X POST https://$DOMAIN/api/auth/login \
  -H 'content-type: application/json' -d '{"username":"...","password":"..."}'   # 204
curl -fsS -b /tmp/penny.jar https://$DOMAIN/api/me                                # household json
rm /tmp/penny.jar
```

A 401 from `/api/me` right after a 204 from login means the cookie was signed and then not accepted
— look at `SESSION_SECRET` having changed between the two requests (a redeploy mid-flight), not at
the browser.

**OpenAI wiring**, without spending anything (it never returns the key):

```sh
curl -fsS https://$DOMAIN/api/ai/status
```

**GOWA over private networking.** Private DNS is runtime-only, so this has to be asked from inside
the service — that is the point of the check:

```sh
railway ssh --service penny -- \
  python -c "import os,httpx;print(httpx.get(os.environ['GOWA_URL']+'/health',timeout=5).text)"
```

`OK` means penny can reach the sidecar. A hang or a connection refusal is almost always `PORT` not
being set on `gowa` (see [Traps](#things-that-will-bite-you), #3).

Once a household exists and a group is linked, `GET /api/whatsapp/status` reports the same thing
end-to-end (`gowa_available`, `is_connected`, `is_logged_in`) behind the session cookie.

**Logs**, if any of the above disappoints:

```sh
railway logs --service penny --lines 100
railway logs --service penny --build --lines 100
```

## 5. Rolling back

**Application code.** With the GitHub source connected, a rollback is a revert:

```sh
git revert <bad-sha> && git push          # Railway autodeploys the revert
```

Faster, without a commit: open the `penny` service in the dashboard, find the last good deployment
and hit Redeploy. `railway deployment list --service penny --json` gives you the ids and statuses to
choose from.

**Migrations do not roll back with the image.** `alembic upgrade head` runs in `railway.json`'s
`preDeployCommand`, so by the time you notice, it has already applied. Reverting the code leaves the
new schema in place. If the old code cannot run against the new schema you must downgrade
deliberately, and check first that the migration has a real `downgrade()`:

```sh
railway ssh --service penny -- alembic current
railway ssh --service penny -- alembic downgrade -1
```

This is why additive migrations (add a nullable column, backfill, then make it NOT NULL in a later
release) are worth the extra deploy.

**Variables.** A variable change restarts the service without rebuilding, so putting the old value
back is the whole rollback: `railway variable set KEY=old --service penny`.

**GOWA.** The image tag is pinned in `infra/provision.py` (`GOWA_IMAGE`). Rolling it back means
changing that constant and re-running the provisioner, or
`railway service source connect --image <old-tag> --service gowa`. The whatsmeow session lives in
Postgres, not on the volume, so an image change does not cost you a re-pair.

**`railway down` is not a rollback.** It removes the most recent deployment and leaves the service
with nothing running.

## Operational levers

Both live in `backend/app/config.py` and are documented in
[`infra/variables.md`](../infra/variables.md#the-one-exception-operational-levers). Their production
values are the code defaults; you set them on Railway **only** to hold a different value, and take
the override away when the incident is over.

**`ONBOARDING_ENABLED=false` — the kill switch.** Adding Penny to a WhatsApp group provisions that
group's household and posts the credentials into the group. `false` restores the old behaviour: an
unknown group is a silent 200 with nothing written. Existing households are untouched. Reach for
this first if the WhatsApp number gets out.

```sh
railway variable set ONBOARDING_ENABLED=false --service penny      # restarts, no rebuild
```

**`ONBOARDING_MAX_HOUSEHOLDS` — the cap** while onboarding is on. The exposure is the **OpenAI
bill**, not data: anyone who learns the number can mint households, and every household runs
extraction, so unbounded signups starve the real families of budget. Lower it; do not remove it.

Nearby, and worth knowing before you touch either: `STARTUP_QUIET_PERIOD_SECONDS` and
`JOIN_BURST_WINDOW_SECONDS` are what stop whatsmeow's app-state replay — which re-emits
`JoinedGroup` for every group the account was already in, on **every deploy** — from provisioning a
household and posting a password into each one. Setting them to 0 is only safe on a number that
belongs to no other groups.

## Things that will bite you

Every one of these was found the hard way, in production, on the night this was first deployed.
They are encoded in `infra/provision.py` so you should not meet them again — this list is here for
when you are working outside the script.

**1. `${{Postgres.PGPASSWORD}}` must never pass through a shell.** Bash sees a brace expansion
around a parameter expansion and rewrites it, silently, and the service boots with a broken value
that fails somewhere unrelated ten minutes later. This is the single reason the provisioner is
Python: every command is an argv list with `shell=False`, so nothing capable of expanding it is in
the pipeline. If you must do it by hand, single-quote the whole assignment and check the stored
value afterwards.

**2. GOWA's `DB_URI` cannot be `${{Postgres.DATABASE_URL}}`.** Two independent reasons, both hard
startup failures: the scheme must be `postgres:` (GOWA prefix-checks it and **panics** on Railway's
`postgresql://`), and it needs `?sslmode=disable` (lib/pq defaults to `require` with no plaintext
fallback, and Railway's internal Postgres does not terminate TLS). Compose it from the `PG*`
variables — the exact string is in [`infra/variables.md`](../infra/variables.md).

**3. `${{svc.PORT}}` does not auto-resolve.** It resolves neither to the port a service listens on
nor to the `PORT` Railway injects at runtime. Set `PORT` by hand on anything called privately —
`PORT=8000` on `penny`, `PORT=3000` on `gowa` — or you get `http://penny.railway.internal:` with an
empty port. The #1 silent private-networking failure.

**4. `APP_HOST=[::]`, with the brackets.** GOWA builds the listen address as
`APP_HOST + ":" + APP_PORT`, so a bare `::` yields `:::3000`, fails `net.SplitHostPort` with "too
many colons in address", and crashes at startup. The same applies to gunicorn's `--bind [::]:$PORT`.

**5. `APP_BASIC_AUTH` is split on `:` and `Fatalln`s unless it gets exactly two parts.** A `:` in
the password is a hard startup crash; `,` separates user pairs. Generate hex and neither is possible.

**6. `railway.json` must not set `deploy.startCommand`.** Railway runs that field **without a
shell**, so `$PORT` arrives at gunicorn as four literal characters and every replica dies with
`'$PORT' is not a valid port number`. The Dockerfile `CMD` wraps it in `sh -c` and is the single
start command. The provisioner's preflight refuses to run if the field reappears.

**7. `railway variable --set` echoes the value back.** That is how an OpenAI key once ended up in a
transcript. Pipe it to `/dev/null`, or better, use stdin so the value never reaches argv either:

```sh
printf %s "$KEY" | railway variable set OPENAI_API_KEY --stdin --service penny >/dev/null
```

**8. `railway volume add` has no `--service` flag.** It attaches to whichever service the current
directory is **linked** to. `railway service link gowa` first, then `railway volume add -m /app/storages`,
then link back. (Verified against `railway volume add --help` on CLI 5.27.0.)

**9. `railway init` needs `--workspace` non-interactively** or it prompts and hangs. And if the
workspace's trial has expired — the personal workspace is the usual culprit — it fails with *"Your
trial has expired"*. Create the project in a paid workspace.

**10. `gowa` must never keep a public domain.** `/health` and `/statics` are registered *before* its
basic-auth middleware, so the login QR PNG is publicly fetchable by URL. It gets a domain for the
ten minutes it takes to pair, and then that domain is deleted. The provisioner warns on every run
if one is still attached.

**11. Private networking is runtime-only.** Not available during build, which is why migrations run
in `preDeployCommand` and never in a Dockerfile step.

**12. Volumes mean downtime on every redeploy.** Railway prevents two deployments being mounted to
the same service at once, so healthchecks buy no zero-downtime here. This is confined to `gowa`:
`penny` has no volume and keeps rolling deploys, and a `gowa` restart only pauses ingest.

**13. Pin the GOWA image tag, and expect to bump it.** `latest` is a mutable manifest re-pointed
every 1–3 weeks (v8→v9 moved the UI out of the image entirely). But the pin is short-lived by
nature: the "client outdated (405)" failure — WhatsApp rejecting a stale hardcoded client version,
after which QR generation silently stops working — is only fixable by upgrading. Budget a monthly
bump.

**14. Healthchecks come from `healthcheck.railway.app`.** If `TrustedHostMiddleware` is ever added
to `penny`, allowlist that hostname or every deploy fails with "healthcheck failed with status 400".
Healthchecks are not continuous; Railway stops polling once the deploy goes live.
